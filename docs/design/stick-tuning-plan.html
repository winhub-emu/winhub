Left / right stick sensitivity and deadzone

Requested by a tester. This page shows how sticks behave today, how they will behave after the change, how the data flows, what gets touched, and how it gets tested. The playground in section 4 runs the real formulas, so you can feel the difference before any code is written.

1Summary

Every physical gamepad stick is currently gated by one fixed number, 15%, hard coded, per axis, with no scaling. After the change each stick has its own deadzone and sensitivity, per container with a per-game override, and a new edge style that removes the jump at the deadzone border.

Per stick
Left and right have their own deadzone (0 to 50%) and sensitivity (0.50x to 2.00x).
Per container + per game
Stored the same way gyro settings are stored. A game can override the container, or inherit it.
Nothing changes by default
Defaults are 15%, 1.00x and the Classic edge style. Output is identical to today until a user touches a slider.
Correction to my earlier chat message I wrote that a sensitivity below 1 would be "more responsive". That was backwards for how people read the word. In this plan higher sensitivity = stick reacts more for the same push. 0.50x is finer and slower, 2.00x is quicker. The playground uses this meaning.

What is wrong with it

#ProblemWhat the player feels
1Not configurable. 15% is baked in.Worn or drifty sticks need more, precise sticks need less. Nobody can change it. This is the tester's request.
2No rescale. Output jumps from 0 to 0.15 the moment the cut is crossed.A dead patch, then a sudden step. Slow aiming or slow walking feels notchy.
3Square deadzone (per axis).Pushing diagonally near centre can move one axis and not the other, so slow diagonals "snap" to a straight line.
4No response curve.Output is exactly linear. A game with a twitchy or a sluggish curve cannot be compensated for.
5Left and right share one value.Left stick for movement and right stick for camera usually want different settings.
6The cut is applied twice on the remap path.Today harmless because both are 0.15. Once the first one is configurable, the second would silently override it (see risk R1).
What already works and staysThe on-screen (touch) sticks have their own per-element deadZone (ControlElement.setDeadZone, saved in the controls profile). They are not touched. Gyro settings are not touched.

The maths (exactly what the code will do)

Inputs: raw stick (x, y) in -1..1, deadzone dz in 0..0.50, sensitivity s in 0.50..2.00. Output: (x', y').

Edge styleSteps
Classic
default		 Per axis, exactly like today but with your numbers:
a = |v|; if a < dz then 0; else sign(v) * min(1, a)^(1/s).
With dz = 0.15 and s = 1.00 this is bit for bit today's output.
Smooth
opt in		 Radial, both axes together:
m = hypot(x, y); if m < dz then (0, 0);
t = clamp((m - dz) / (1 - dz), 0, 1) (starts at 0 just past the edge, reaches 1.0 at full push);
t' = t^(1/s); output (x/m * t', y/m * t').
  • Sensitivity is a response curve, not a multiplier. A plain "x 1.5" would clip at full push and lose the top end. With the exponent, full push is always exactly 1.0 and zero is always 0. s > 1 lifts the middle (more reaction for small pushes). s < 1 flattens it (finer control).
  • Direction is never changed in Smooth mode: the output points the same way as the raw stick, only its length is reshaped. That is what removes the "snapping to a line" problem.
  • Output length is clamped to 1.0. Square-gate controllers that report up to about 1.41 on diagonals cannot overshoot.
  • Non-finite input (NaN, infinity) returns (0, 0). Settings outside range are clamped on read.

Where the numbers come from at launch

Container extrasEdited in the container editor.
Shortcut extras (optional)If the shortcut has the key, it wins. If not, it inherits the container. Same rule as gyro sensitivity in XServerDisplayActivity.java around 2538 to 2566.
Resolved once when the game session startsThe five numbers are handed to each ExternalController through one setter (setStickTuning). Controllers that connect later get them on attach, so a pad plugged in mid game is tuned too. The fields are volatile, because input arrives on the UI thread and the writers read on another.
Steam Controller backendIts raw floats go through the same shaper using the pad's ExternalController, so both paths behave identically and the duplicate deadZone() is no longer used for sticks.

  • Sliders step 1% for deadzone and 0.05x for sensitivity. Values are written to the model on change and saved with the existing save action, nothing new to remember.

8Compatibility and safety

  • Existing users see no change. No key present = defaults = Classic, 15%, 1.00x = today's exact output (a unit test asserts this for a grid of inputs).
  • Old containers and shortcuts load as before. Unknown extras are already preserved. No migration, no schema change, no Room change.
  • Downgrade safe: an older app version simply ignores the five extras.
  • Sharing: the five keys are added to the config export lists (communityconfigs/ConfigExporter.kt, communityconfigs/ShortcutExporter.kt) so a shared config carries the tuning. Imports of configs without the keys keep working.
  • Threading: settings fields are volatile, the shaper is a pure static function, nothing allocates per event beyond what the code does today.
  • No new permissions, libraries, network calls or native code. Wine, box64, drivers and the rootfs are untouched.
  • Not touched: touch overlay sticks, gyro, triggers, D-pad hat values, binding maps, controls profiles format.

10Edge cases

CaseBehaviour
Deadzone 0%Everything past the hardware flat gate passes. Fine for good sticks. Drift is then the controller's problem, and the help text says so.
Deadzone 50%Upper limit. In Smooth mode the usable range is 0.5 to 1.0, still reaches full output. Never 100%, so full push can never be unreachable.
Sensitivity 0.50x / 2.00xCurve exponent 2.0 and 0.5. Zero stays zero, full stays one.
Controller with a huge hardware flatThe hardware gate runs first, then ours. They do not add up in a visible way unless the flat is bigger than our deadzone, in which case the larger one wins.
Square gate reporting 1.41 on diagonalSmooth clamps the length to 1.0. Classic clamps each axis to 1.0.
Controller sends many historical samplesShaper is stateless, called per sample, no ordering problem.
Two controllers at onceEach ExternalController holds its own copy of the same numbers. Both are tuned.
Hot plug / unplugTuning applied on attach. Nothing is stored on the device object that outlives it.
Corrupt extra ("abc", "", "NaN", "9999")Falls back to default or is clamped. Never throws.
Shortcut with override offThe shortcut extras are absent, so the container values are used.
Process death mid editValues only exist in the editor until saved, same as every other setting in those screens.
Rotating the device in the editorState lives in the ViewModel / remembered state like the gyro sliders.

11How it gets tested

I cannot build or run anything in this setup, so the unit tests are written for you to run, and the manual list is for your testers.

Unit tests (new, JUnit, no Android classes needed)

  • Identity at defaults: for a grid of x, y from -1 to 1 in 0.01 steps, Classic with 0.15 and 1.00x equals today's abs(v) >= 0.15 ? v : 0 per axis.
  • Zero stays zero, full stays one for every sensitivity from 0.50 to 2.00.
  • Monotonic: output length never decreases as push increases (all styles, all settings).
  • Smooth is continuous at the border: just inside gives 0, just outside gives roughly 0.
  • Direction preserved in Smooth mode (angle in equals angle out).
  • Clamp and garbage: NaN, infinity, out of range settings, 1.41 diagonal.
  • Remap overload equivalence: old gate and new gate give identical results on any value the old pipeline could produce.
  • Container getters: missing, empty, bad and out of range extras.

Manual list for testers

  1. Fresh install and an existing install: sticks feel exactly as before without touching anything.
  2. Controller test screen: left deadzone to 30%, small pushes show 0, shaped column matches the playground.
  3. Same game, left 8% and right 25%: movement is sensitive, camera ignores drift.
  4. Switch to Smooth: slow walk has no step at the start.
  5. Per-game override on/off, then relaunch: correct values each time.
  6. Plug a second pad mid game: it uses the same tuning.
  7. Steam Controller (if available): same feel as a normal pad.
  8. Remap sticks to keys or other gamepad buttons: a 5% deadzone really activates at 5%.
  9. Export a config, import it on another device: the five values come across.
  10. Whole UI with the controller only, no touch.

12Risks, and what I do about each

#RiskPlan
R1The second 0.15 gate in InputControlsView (remap path) would silently override a smaller user deadzone and double up a larger one.Threshold overloads, old signatures kept, equivalence unit test. This is the riskiest touch point, so it gets the most careful review.
R2I have not yet traced every consumer of the values in the remap map (buttons or other sources might also feed it).Before editing I grep all callers of the four methods. If any non-stick source flows through, that source keeps the old threshold.
R3Controllers created in places I have not listed (for example the controller test and the bindings screen each have their own instance).Grep every new ExternalController and every updateStateFromMotionEvent caller. Each either gets tuning or deliberately keeps defaults.
R4Users picking silly values and thinking the app is broken.Ranges are capped, help text names the symptom ("stick drifts: raise deadzone"), reset buttons are one press.
R5Games that apply their own deadzone on top.Documented in the help text. Users who want pure raw input can set 0%.
R6I cannot build. A compile error would waste your CI run.Mental compile pass (imports, nullability, every signature and call site) plus a re-read of the full diff before I hand it over.

13Decisions and out of scope

Decisions I still need from you (recommended answer first)

  1. Per-game override as well as container? Recommended: yes.
  2. Adjust from the in-game drawer, like gyro? Recommended: not now. It is extra work (live apply + persist), the editors already cover it.
  3. Touch overlay sticks? Recommended: leave alone, they already have a per-element deadzone.
  4. Default edge style. Recommended: Classic, so nothing changes silently. Switch to Smooth by default later once testers confirm they like it.

Ideas I am not putting in this change

  • Outer deadzone / max range (for sticks that never reach 1.0).
  • Per axis invert, swap sticks, trigger deadzone.
  • Per controller (by device id) profiles instead of per container.
